\section{Overview}

BSP Registry Tools is a Python CLI and library for managing Board Support
Packages (BSPs) for embedded Linux systems based on Yocto Project or Isar
(Debian-based). It uses a YAML registry (schema~v2.0) as the single source of
truth for all configuration, enabling reproducible, team-shareable builds across
dozens of boards and release combinations.

\begin{itemize}
  \item Python CLI tool (\texttt{bsp}) and importable Python API (\texttt{BspManager})
  \item YAML registry v2.0 --- devices, releases, features, presets, environments
  \item Wraps KAS (\texttt{kas} / \texttt{kas-container}) for Yocto and Isar builds
  \item Zero-config first run --- auto-clones the Advantech registry on first use
  \item Named remote management --- save/reuse remote registries like git remotes
  \item Environment variable expansion via \texttt{\$ENV\{VAR\}} in registry YAML
  \item Cloud artifact deploy / gather (Azure Blob Storage, AWS S3)
  \item HTTP server with REST + GraphQL APIs (FastAPI + Strawberry)
  \item Shell tab completions for all arguments (Bash, Zsh, Fish, tcsh)
  \item HIL test triggering via LAVA with Robot Framework suites
  \item Interactive registry editor (\texttt{bsp registry add/edit/remove})
  \item Registry validation, diff, and split across multiple files
\end{itemize}

\section{Registry Schema v2}
\label{sec:registry}

The registry uses a YAML file (default: \texttt{bsp-registry.yml}) with schema
version 2.0. The top-level structure is:

\begin{lstlisting}[language=YAML]
specification:
  version: "2.0"          # required; tool exits on mismatch

include:                  # optional -- list of additional YAML files to merge
  - devices/boards.yaml
  - releases/scarthgap.yaml

environment:              # optional -- global env vars for every build
  variables:
    - name: "DL_DIR"
      value: "$ENV{HOME}/downloads"
  copy:                   # optional -- files copied before every build
    - scripts/global-setup.sh: build/

environments:             # optional -- named build environments (dict)
  default:
    container: "ubuntu-22.04"
    variables:
      - name: "SSTATE_DIR"
        value: "$ENV{HOME}/sstate"

containers:               # optional -- Docker image definitions (dict)
  ubuntu-22.04:
    image: "bsp/kas:5.2"
    file: Dockerfile

registry:
  frameworks: [...]       # build-system framework defs (Yocto, Isar)
  distro: [...]           # distribution defs (Poky, fsl-imx-xwayland, ...)
  vendors: [...]          # cross-release vendor KAS fragments
  devices: [...]          # hardware board definitions
  releases: [...]         # Yocto / Isar release definitions
  features: [...]         # optional add-ons
  bsp: [...]              # named presets (device + release + features)

deploy:                   # optional -- cloud artifact upload config
  provider: azure         # "azure" (default) or "aws"
  container: bsp-artifacts
  prefix: "{vendor}/{device}/{release}/{date}"
\end{lstlisting}

\subsection{Registry Sections Summary}

\begin{tabularx}{\linewidth}{L{36mm}X}
  \rowcolor{tableheadbg}
  \textbf{Section} & \textbf{Purpose} \\
  \toprule
  \rowcolor{roweven} \texttt{frameworks}   & Build-system definitions (Yocto, Isar); referenced by distros \\
  \rowcolor{rowodd}  \texttt{distro}       & Distribution definitions (Poky, fsl-imx-xwayland, \ldots) \\
  \rowcolor{roweven} \texttt{vendors}      & Cross-release board-vendor KAS fragments \\
  \rowcolor{rowodd}  \texttt{devices}      & Hardware board definitions (slug, vendor, SoC, KAS includes) \\
  \rowcolor{roweven} \texttt{releases}     & Yocto/Isar release definitions with optional vendor overrides \\
  \rowcolor{rowodd}  \texttt{features}     & Optional composable add-ons (OTA, secure-boot, ROS2, \ldots) \\
  \rowcolor{roweven} \texttt{bsp}          & Named presets = device + release(s) + features \\
  \rowcolor{rowodd}  \texttt{environments} & Container + variable bundles per build class \\
  \rowcolor{roweven} \texttt{containers}   & Docker image definitions with optional volume mounts \\
  \rowcolor{rowodd}  \texttt{deploy}       & Cloud artifact upload configuration (Azure / AWS) \\
  \rowcolor{roweven} \texttt{include}      & Split large registries across multiple files \\
  \bottomrule
\end{tabularx}

\subsection{File Splitting with \texttt{include}}

Large registries can be split across multiple YAML files using the top-level
\texttt{include} directive.  Each included file is merged before the root file's
own content is processed.

\begin{tabularx}{\linewidth}{L{28mm}X}
  \rowcolor{tableheadbg}
  \textbf{Data type} & \textbf{Merge behaviour} \\
  \toprule
  \rowcolor{roweven} Lists (devices, releases, \ldots)
    & Concatenated --- included items appear before the including file's items \\
  \rowcolor{rowodd}  Dicts (containers, environments)
    & Merged recursively --- including file wins on conflicting keys \\
  \rowcolor{roweven} Scalars
    & Including file wins \\
  \bottomrule
\end{tabularx}

\begin{notebox}
  Included files can themselves contain \texttt{include} directives
  (paths are always resolved relative to the file containing the directive).
  Circular includes are detected at load time.
  The \texttt{specification} block is silently stripped from included files.
\end{notebox}

registry:
  devices:
    - slug: rsb3720          # unique identifier
      description: "Advantech RSB-3720 (i.MX8M Plus, 6GB)"

      soc_vendor: nxp

        - vendors/advantech-europe/nxp/machine/imx8/rsb3720.yml

\end{lstlisting}

\begin{tabularx}{\linewidth}{L{28mm}L{18mm}X}
  \rowcolor{tableheadbg}
  \textbf{Field} & \textbf{Type} & \textbf{Description} \\
  \toprule
  \rowcolor{roweven} \texttt{slug}        & string   & Unique identifier; used in CLI and presets \\
  \rowcolor{rowodd}  \texttt{vendor}      & string   & Board vendor name \\
  \rowcolor{roweven} \texttt{soc\_vendor} & string   & Silicon vendor (for compatibility checks) \\
  \rowcolor{rowodd}  \texttt{soc\_family} & string?  & SoC family (for compatibility checks) \\

  \rowcolor{roweven} \texttt{copy}        & list     & Files to copy before each build \\

\subsection{Vendor Overrides}

Vendor overrides let a single release slug (e.g.\ \texttt{scarthgap}) apply
different KAS fragments, distro settings, and kernel/firmware version pins per
hardware vendor and SoC family.

\subsubsection{Basic Vendor Override}

\begin{lstlisting}[language=YAML]
releases:
  - slug: scarthgap
    distro: poky
    includes:
      - kas/scarthgap.yaml
    vendor_overrides:
      - vendor: advantech-europe
        distro: fsl-imx-xwayland   # overrides release.distro for this vendor
        includes:
          - kas/advantech-europe/scarthgap-vendor.yaml
        releases:                  # optional kernel/firmware sub-releases
          - slug: imx-6.6.52-2.2.2
            includes:
              - kas/advantech-europe/nxp/imx-6.6.52-2.2.2-scarthgap.yml
          - slug: imx-6.12.0
            includes:
              - kas/advantech-europe/nxp/imx-6.12.0-scarthgap.yml
\end{lstlisting}

\subsubsection{SoC Vendor Overrides}

When a board vendor ships hardware based on multiple SoC families, the
\texttt{soc\_vendors} list selects per-SoC-family KAS fragments automatically
by matching the device's \texttt{soc\_vendor} field:

\begin{lstlisting}[language=YAML]
vendor_overrides:
  - vendor: advantech
    includes:
      - kas/advantech/scarthgap-common.yaml  # common for all Advantech boards
    soc_vendors:
      - vendor: nxp
        distro: fsl-imx-xwayland
        includes:
          - kas/advantech/nxp/scarthgap.yaml
        releases:
          - slug: imx-6.6.53
            includes: [kas/advantech/nxp/imx-6.6.53.yaml]
          - slug: imx-6.12.0
            includes: [kas/advantech/nxp/imx-6.12.0.yaml]
      - vendor: mediatek
        distro: mt-distro
        includes:
          - kas/advantech/mediatek/scarthgap.yaml
\end{lstlisting}

\subsubsection{KAS Include Ordering}

The resolver assembles the final KAS file list in this order:

\begin{enumerate}
  \item \texttt{framework.includes}
  \item \texttt{distro.includes}
        (uses \texttt{SocVendorOverride.distro} $>$ \texttt{VendorOverride.distro} $>$
         \texttt{Release.distro})
  \item \texttt{vendors[device.vendor].includes}
  \item \texttt{release.includes}
  \item \texttt{VendorOverride.includes}
  \item \texttt{SocVendorOverride.includes}
  \item \texttt{VendorRelease.includes} (sub-release, if \texttt{vendor\_release} is set)
  \item \texttt{device.includes}
  \item \texttt{feature.includes} (for each enabled feature)
  \item \texttt{feature.VendorOverride.includes}
  \item \texttt{feature.SocVendorOverride.includes}
  \item \texttt{feature.VendorRelease.includes}
\end{enumerate}

\subsection{Named Environments}

Named environments bundle a container with environment variables and setup
file-copy entries under a single name, referenced by releases:

\begin{lstlisting}[language=YAML]
environments:
  default:                    # used when release has no environment field
    container: "ubuntu-22.04"
    variables:
      - name: "DL_DIR"
        value: "$ENV{HOME}/data/cache/downloads"
      - name: "SSTATE_DIR"
        value: "$ENV{HOME}/data/cache/sstate"
    copy:
      - scripts/env-setup.sh: build/

  isar-build:                 # named environment for Isar releases
    container: "isar-debian-13"
    variables:
      - name: "DL_DIR"
        value: "$ENV{HOME}/data/cache/isar-downloads"
    copy:
      - isar/scripts/isar-runqemu.sh: build/
\end{lstlisting}

Container priority: \texttt{device.build.container} (highest) $>$
named environment container $>$ none (bare \texttt{kas} run). \\
Variable merge order: root \texttt{environment.variables} $\to$
named environment variables $\to$ feature \texttt{env} variables (feature wins).

\section{Feature System}

Features are optional, composable add-ons mixed into any BSP preset. They
support device compatibility constraints, framework/distro restrictions,
release-specific includes, and vendor-specific includes.

\begin{lstlisting}[language=YAML]
registry:
  features:
    - slug: rauc
      description: "Enable RAUC OTA update support"
      compatible_with: [yocto]   # only compatible with Yocto framework
      compatibility:
        soc_vendor: [nxp]        # allow-list: only NXP SoC devices
      includes:
        - features/ota/rauc/rauc.yml
      local_conf:
        - "DISTRO_FEATURES:append = ' rauc'"
      env:
        - name: "RAUC_KEY_FILE"
          value: "$ENV{RAUC_KEY_FILE}"
      vendor_overrides:
        - vendor: advantech-europe
          includes:
            - features/ota/rauc/advantech-rauc.yml
          soc_vendors:
            - vendor: nxp
              includes:
                - features/ota/rauc/modular-bsp-ota-nxp.yml
              releases:
                - slug: imx-6.6.53
                  includes:
                    - features/ota/rauc/rauc-imx-6.6.53.yml
      release_overrides:
        - release: scarthgap
          includes:
            - features/ota/rauc/rauc-scarthgap.yml
\end{lstlisting}

\subsection{Release Overrides}

A feature can include different KAS files per Yocto/Isar release. The include
order for a feature with both \texttt{release\_overrides} and
\texttt{vendor\_overrides} is:

\begin{enumerate}
  \item \texttt{feature.includes} (always applied)
  \item \texttt{feature.release\_overrides[release].includes} (when release slug matches)
  \item \texttt{feature.VendorOverride.includes}
  \item \texttt{feature.SocVendorOverride.includes}
  \item \texttt{feature.VendorRelease.includes}
\end{enumerate}

\section{Python API}

All CLI operations are backed by a public Python API. The primary entry point
is \texttt{BspManager}, which coordinates registry loading, preset resolution,
builds, deployment, and artifact gathering.

\subsection{Basic Usage}

\begin{lstlisting}[language=Python]
from bsp import BspManager, RegistryFetcher, V2Resolver

# 1. Fetch / update the remote registry
fetcher = RegistryFetcher()
registry_path = fetcher.fetch_registry(
    repo_url="https://github.com/Advantech-EECC/bsp-registry.git",
    branch="development",
    update=True,
)

# 2. Load registry and inspect contents
manager = BspManager(str(registry_path))
manager.initialize()

for dev in manager.model.registry.devices:
    print(dev.slug, "-", dev.description)

for rel in manager.model.registry.releases:
    print(rel.slug, rel.yocto_version)
\end{lstlisting}

\subsection{Building and Deploying}

\begin{lstlisting}[language=Python]
from bsp import BspManager

manager = BspManager("bsp-registry.yaml")
manager.initialize()

# Build a named preset
result = manager.build_bsp("modular-bsp-rsb3720", release="walnascar")
print("Build exited with:", result.returncode)

# Deploy artifacts to cloud storage
deploy_result = manager.deploy_bsp("modular-bsp-rsb3720")
for artifact in deploy_result.uploaded:
    print("Uploaded:", artifact.name, "->", artifact.url)

# Gather (download) previously uploaded artifacts
gather_result = manager.gather_bsp("modular-bsp-rsb3720", release="walnascar")
for path in gather_result.downloaded:
    print("Downloaded:", path)
\end{lstlisting}

\subsection{Resolving a Configuration}

\begin{lstlisting}[language=Python]
from bsp import BspManager, V2Resolver

manager = BspManager("bsp-registry.yaml")
manager.initialize()

resolver = V2Resolver(manager.model)
config = resolver.resolve(
    device_slug="rsb3720",
    release_slug="walnascar",
    feature_slugs=["systemd", "security", "rauc"],
)

# Inspect the resolved KAS file list
for f in config.kas_files:
    print(f)

# Inspect environment variables
for var in config.env_vars:
    print(f"{var.name}={var.value}")
\end{lstlisting}

\subsection{Multi-Registry Mode}

\begin{lstlisting}[language=Python]
from bsp import BspManager

manager = BspManager(
    config_paths=[
        ("advantech",    "/path/to/advantech-registry.yaml"),

    ]

\section{Extending BSPs with Custom Yocto Layers}

Export a resolved KAS configuration and include it in a downstream project to
add custom meta-layers without modifying the registry:

\begin{lstlisting}[language=Bash]
# Export the resolved KAS config for a specific preset + release
bsp export modular-bsp-rsb3720 --release walnascar \
  > modular-bsp-rsb3720-walnascar.yaml
\end{lstlisting}

\begin{lstlisting}[language=YAML]
# my-custom-kas.yaml
header:
  version: 19
  includes:
    - repo: bsp-registry
      file: modular-bsp-rsb3720-walnascar.yaml  # from bsp export

repos:
  bsp-registry:
    url: "https://github.com/Advantech-EECC/bsp-registry"
    branch: "development"
    layers: { .: "disabled" }

  meta-custom:
    layers:
      meta-custom:    # your custom Yocto meta-layer
\end{lstlisting}

\begin{lstlisting}[language=Bash]
# meta-custom/recipes-core/images/imx-image-%.bbappend
# CORE_IMAGE_EXTRA_INSTALL += "mpv"
# LICENSE_FLAGS_ACCEPTED += "commercial"

# Build with your extension
kas build my-custom-kas.yaml
\end{lstlisting}
